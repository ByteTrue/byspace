# 全量重审

> **读者：** 接手「确认 Go 版真的和 Node 版行为一致」的人。

## 为什么还要再来一次

[2026-10-19 的 epic](../epics/2026-10-19-x-go-single-binary-full-parity/spec.md) 做过一轮
512 文件审计，结论全在
[audit-log](../epics/2026-10-19-x-go-single-binary-full-parity/issues/audit-log.md)。
[2026-10-22 的 epic](../epics/2026-10-22-x-node-to-go-functional-port/spec.md) 又把当时判为
`MISSING` 的六个子系统实现掉了。

两轮之后仍然要求重审，原因很简单：**前两轮的判据是「Go 有没有对应物」，不是「Go 的行为是否
一致」**。两者差别很大：

- `PORTED` 可能只是「函数名对上了」——真实参数被忽略、返回字段填了假值、分支顺序不同。
- 上一轮自己在 `audit-log` 里写过结论强度分层：只有几十个文件是逐行读的，`commands/` 与
  `utils/` 读的是导出面，`test-utils`/`*-facts.ts`/`schema.ts` 按类别判定。
- 事实上每补一个 flag / 字段，就会浮出一批语义错误（`provider` 硬编码、`daemon stop` 对改名
  二进制不发信号、校验在拨号之后、`agent open` 路由到 `inspect`）。

所以这一轮的标准只有一个：**打开 Node 文件，逐函数读，然后在 Go 里确认这个函数做的每件事都
真的做了**。不接受「有对应实现」作为结论。

## 判定

每个文件给一条结论，并且**结论必须指向具体的 Go 位置和行为说明**：

| 结论      | 含义                                                     |
| --------- | -------------------------------------------------------- |
| `MATCH`   | 逐个导出函数核对过，行为一致。要写出对应关系             |
| `FIXED`   | 核对时发现不一致，已改并加了反向验证过的测试             |
| `N/A`     | 无运行时行为（类型定义、测试辅助、构建产物）。要写为什么 |
| `DROPPED` | 已被正式决策移除。必须给 issue 编号 + commit             |

`MISSING` 不允许出现在最终结论里——缺就实现。

## 记录

账本在 [`node-reaudit-log.md`](node-reaudit-log.md)，一行一个文件，带函数级说明。

## 与前两轮的关系

- 前两轮的结论**不能直接采信**，只能当线索（哪里最可能有差异）。
- 前两轮的测试与实现**保留**，本轮发现的问题在那里修。
- 本 issue 只做一件事：核对。修完了在账本里记 `FIXED`，不另开 issue。

## 完成判据

1. 512 个文件全部有结论，无 `MISSING`。
2. 每个 `MATCH` 都能指出 Go 的具体位置与行为对应。
3. `npm run audit` 全绿：`go test ./...`、出站四项全 0、入站缺口 0、浏览器 10/10。
