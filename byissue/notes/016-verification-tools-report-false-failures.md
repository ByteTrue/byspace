# 假失败：验证工具的前置状态

## 症状

`npm run audit` 的浏览器检查从 10/10 掉到 2/4，再掉到 7/8，失败项在
`Chief is pinned above ordinary projects`、`Open settings`、`Open thinking menu` 之间轮换。
同一份代码单独跑脚本又经常 10/10。

第一反应是「上一轮改动引入了回归」。实际不是：应用会从存储恢复上次的**全屏会话视图**，
快照里只有 `Open menu` 一个按钮，脚本要找的 `Settings` 和 `Select thinking option` 根本还
不存在。**侧栏的开合是浏览器恢复的状态，不是脚本设置的。**

## 判据

一次失败要归到三类之一，处理方式完全不同：

| 类别               | 例子                                 | 处理                   |
| ------------------ | ------------------------------------ | ---------------------- |
| 被测行为真的坏了   | 消息发出去没有流式响应               | 修产品                 |
| 无关前置条件不满足 | 侧栏没开所以找不到 Settings          | 把前置条件摆成已知状态 |
| 工具自身不稳       | 断言的读法错、可访问性树把目标折叠了 | 换一种读法             |

第二类和第三类的区别在于：**第二类是环境状态，第三类是观测方式**。前者可以消除前置条件，
后者必须改断言。

## 怎么不滑成「为了让检查变绿而放宽断言」

本次的做法：加 `ensureSidebarVisible()`，只做「如果 `Open menu` 在就点它；如果
`Close menu` 在就说明已经开着」——**后续关于思考档位的断言一条没动**。判断标准是：

> 消除前置条件之后，原来的断言是否**仍然能失败**？

能失败就是消除了噪声；不能失败（比如把「找不到按钮」改成跳过）就是放宽了断言。

反向验证：连续跑三次都是 10/10，且单独跑也是 10/10。如果只是「有时候绿」，那说明消除得不够。

## 第三类：跑的不是刚构建出来的那个二进制

同一轮里还撞过一次：`make build-full` 之后我习惯性 `rm -rf internal/webui/dist/* && touch
internal/webui/dist/.keep`（把产物清掉，保持工作树干净）。二进制里**已经内嵌了**产物，所以
服务本身正常；但 `internal/webui/dist/` 是空的，`ls` 一看像是构建失败，`/api/health` 也正常
响应，`index.html` 只有 3114 字节——看起来像前端没打进去。

差点归因为「构建链断了」。实际判据是**二进制的体积**：`bin/byspace` 19 MB（含前端）、新
`go build` 出来的 14 MB（不含）——体积差就是答案。

同类坑之前也踩过：`go build ./...` **不产出** `bin/byspace`，于是在旧二进制上跑验证，
得出「改动无效」的结论，还做了两次 git bisect 才排除。

判据：验证之前先确认「正在跑的东西是不是刚构建的那个」。二进制体积、`--version`、
进程启动时间是三种便宜的做法。

## 另一类：并发压测造成的抖动

`go test ./...` 单独跑全绿，但在 `npm run audit` 里（同时还在跑 `make build-full` 和
daemon 重启）报两个 pi 流式测试失败：

```
stream_conformance_test.go:376: provider died mid-turn but no turn_failed was emitted
```

这两个测试内部有 3 秒超时，是时序敏感的。判定方法：**单独跑、以及整包跑**，都通过 →
是机器负载下的抖动，不是回归。这类失败要记下来但不要改代码。

反过来，如果单独跑也失败，就不能用「可能是抖动」解释——本次 `TestProcessExitFailsTurnAndReleasesRuntime`
先单独跑失败了一次，我差点归因为负载，重跑四次全过后才确认是并发抖动。

## 教训

- 验证工具报失败时，**先问「它看到的是不是我关心的那个东西」**，再问「产品坏了吗」。
  顺序反了就会去改没有问题的代码。
- 修验证工具时，唯一不能碰的是断言本身。前置条件可以摆，观测方式可以换。
- 时序敏感的测试要能区分「单独失败」和「并发失败」，否则每次 CI 抖动都会诱导一次盲改。
- 本次还抓到一条：单独跑 `node scripts/browser-conformance.mjs` 报 10 项，在 `audit` 里报 8 项
  ——**检查数量本身会变**，说明入口条件不同，比较通过率时要看分母。
