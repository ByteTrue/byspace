# 代理身份与测试开关

> **读者：** 给 BySpace worker 域（或任何"agent 驱动 agent"的域）写验收或接线的人。三条教训都来自同一次交付，每条都被真机探针逼出来，事后看全是可预防的结构问题。

## 1. "我替它跑"不等于"它能自己跑"

验证"协调者会自己拉人"时，我用 CLI 以它的名义敲了命令，然后把结果记为"验证 B 跑通"。**发起方是我，不是 worker。** 这类误报的根源：验证者（我）与被验证者（worker）共用同一控制面时，wire 上没有任何东西区分"这是它的决定"还是"这是我的决定"。

**判据：** 凡是验证"X 会自己做 Y"，证据必须满足两点 —— (a) 我在发起后**没有再敲任何 X 域内的命令**；(b) 产物里有 X 自己的行动痕迹（本域即 run 表里 X 的 run、session 里 X 的 turn）。现在的身份门把这个判据机制化了：从任何 agent 会话（包括我）代跑 worker 命令会被 daemon 直接拒绝 —— **那条误报路径已经不存在**。

## 2. 覆盖开关只挡你想到的那条路

`workerWakeLoop: false` 只挡了 `start()` 里的定时器。但 `sendMessage → onWakeRequested → requestPass()` 直接驱动一趟 pass，不看有没有 start 过。结果：测试 daemon 里 delivery 两秒变 claimed —— **RPC 验证器一直在偷偷起真 agent 烧钱**，还跟自己读的收件箱抢状态。

**判据：** 写"关闭/禁用"开关时，枚举**所有**入口而不仅是最显眼的那个。对新入口的验收：开着开关跑一遍被禁用的行为，观察它确实没发生。探针（发一条消息，看 delivery 状态是否被消费）比读代码快也更可信。

## 3. 契约文档说"等待"，实现就真的要等待

`runPass()` 注释写"coalesced"，实现是"别人在跑就立刻 return"。`start()` 的开箱 pass 因此把测试的显式 pass 合并掉再提前返回 —— 测试红得莫名。根因是**文档承诺了"这一趟做完"而实现只承诺"这一趟开始过"**。

**判据：** async 方法的返回语义（"已排队"还是"已完成"）是契约的一部分，写进注释就要按它实现。容易被咬的形态：`if (inFlight) { flag; return; }` —— 若调用方拿返回点当"完成点"，这里就是竞态。本域的修法是 join in-flight 那趟（含自己被合并的轮次）。

## 共同根源

三条都是**"验证者不诚实对待验证边界"**的变体：把代跑当自跑（身份边界）、把关一路当关全部（入口边界）、把"开始过"当"做完了"（时序边界）。预防结构相同：每条验收先写下"证据必须排除什么"，再去找证据 —— 而不是拿到一个绿结果就问它证明了什么。
