# 主机列表与隧道规则在自己的 daemon 之间同步

## 要改变什么

现状有三个问题。

第一，主机列表存在每个前端自己的浏览器存储里。`web/src/core/runtime/host-runtime.ts` 把整份列表写进 `localStorage` 的 `@byspace:daemon-registry`（第 1274、2020 行）。同一台笔记本上，桌面客户端和浏览器打开的 6777 背后是同一个 daemon，看到的却是两份列表；手机又是第三份。

第二，隧道只有一个方向，也不能在任意两台 daemon 之间建。`internal/tunnel/registry.go` 的 `ForwardConfig{RemotePort, LocalPort}` 只表达「把对端端口拉到本机」，`byissue/spec/connection.md` 的「Daemon 隧道」一节把反向隧道明确划在范围外，`/tunnels` 页面也只能从当前这台 daemon 出发。要让 VPS 上的服务访问笔记本的 3425，今天只能手工维护 ssh 反向隧道。

第三，隧道把对端密码存在发起端。`tunnels.json` 的每个 peer 都存着对端的 `password`，一台机器被攻破，它能连的对端也跟着暴露。

目标：用户的 daemon 组成一条同步链，主机列表和隧道规则在每台 daemon 上都有一份，任何前端连上任何一台都看到同一份；隧道在任意两台 daemon 之间、两个方向都能建，全程不需要打开远端机器的 web；同步的数据里不含任何密码。

## 为什么现在做

用户在 2026-11-12 尝试把 VPS 上的 magpie 接到笔记本的 magpie（3425）时碰到这几个问题。讨论中确认它们有同一个根因：「我有哪些机器、它们之间怎么连」这份状态放在了前端和各台机器的私有文件里，而不是在用户的 daemon 之间共享。

## 当前方案

### 前提：每台 daemon 的远程连接都要有密码

用户 2026-11-12 确认，经 SSH、局域网 IP 或 relay 使用一台 daemon 都必须先设密码。本方案依赖这一点，因为密码是一台 daemon 唯一的钥匙。

现状（读代码得出，未实测）：`internal/server/server.go:593` 只在设了密码时才校验 bearer；局域网监听已经强制先设密码（`spec/connection.md`「安全边界」）；relay 和 SSH 这两条路径还没有「先设密码才能用」的约束。第 0 片补上这个约束。

### 同步链只有 daemon

同步链由用户的 daemon 组成，每台 daemon 存一份完整副本，落在 daemon home 里。手机、浏览器这类没有 daemon 的客户端不是成员，不登记进链。它们连上任意一台 daemon 就拿到整份数据，在本地留一份缓存。客户端清掉缓存只会丢掉本地记住的密码，不会在链上留下任何东西。

### 同步的内容全部是公开信息

- 主机：`serverId`、daemon 公钥、连接地址（relay、局域网、SSH）、标签、外观。
- 成员：哪几台 daemon 在链上，各自的公钥和最后在线时间。
- 隧道规则的展示信息：两端主机、端口、监听地址、标签、是否停用。

不同步任何密码或 token。主题、快捷键、面板宽度、草稿等个人偏好也不同步。

### 客户端：用哪台输哪台的密码

客户端连上任意一台 daemon 后，看到整份主机列表，每台带锁标记。用户点开某台、输入它的密码后才能使用。客户端可以选择在本机记住密码。本机前端（桌面客户端、浏览器打开的 6777）连本机 daemon 时直接读写本机副本，判断本机沿用 058 的回环语义（`web/src/core/hooks/use-is-local-daemon.ts`）。

客户端按主机公钥校验身份。某条主机记录的公钥和客户端上次见到的不一致时，客户端拦下连接，要求用户确认，和 SSH 提示主机密钥变化的做法一样。这样即使有人篡改了同步数据里的地址，用户也不会在不知情的情况下把密码输给假主机。

### daemon 加入和移除

把一台 daemon 加进链：在客户端里用密码同时连上链上的某台 daemon 和这台新 daemon，点「加入我的设备」。用户对两边都出示过密码，授权由此成立，不需要额外的配对码。CLI 对应 `byspace devices add`。

移除：在「设备」页移除某台 daemon。被移除的公钥留一条删除标记，任何成员都不能再把它同步回来。「设备」页显示每台的最后在线时间，退订的机器由用户手动移除。

### 隧道规则与授权

建规则时，客户端必须用密码连着两端。客户端当场写两处：

- 目标端 daemon 本地写一条授权，内容是「允许公钥为 X 的 daemon 访问我的端口 P」。
- 源端 daemon 写一条规则，内容是「在本机某地址的某端口上监听，转发到目标 daemon 的端口 P」。

隧道连接时，源 daemon 用自己的 daemon 密钥证明身份，目标 daemon 查本地授权。授权只存在目标 daemon 本地，只能由出示过密码的客户端写入，不经过同步。同步数据里的规则只用来在 UI 上展示，不代表权限。`tunnels.json` 里的对端密码因此不再需要。

数据通道沿用现有的 `internal/tunnel` 帧协议，它本来就是双向的。要补的是规则模型、目标端授权、daemon 密钥认证。

### 隧道 UI

`/tunnels` 页面改成规则列表。新建规则的表单：

```
端口所在    [ 主机：笔记本 ▾ ]  端口 [ 3425 ]
在这里访问  [ 主机：VPS ▾ ]     监听 [ 127.0.0.1 ▾ ] : [ 18090 ]
标签        [ magpie 上游 ]
```

两个主机下拉框都列出链上所有 daemon，可以任选两台，与客户端当前连着哪台无关。还没输入过密码的主机，选中时先要求输入。列表里每条规则显示两端各自的状态（在线并监听中、离线、授权缺失），哪一端出问题一眼可见。监听地址默认 `127.0.0.1`，可以选别的网卡地址（例如 Docker 网桥，容器访问不到宿主回环时需要），选 `0.0.0.0` 时显示风险提示。

### 合并

- 主机记录用 `serverId` 作键，同一台机器在任何设备上都是同一条记录。
- 合并按记录逐条进行。每条记录带一个逻辑版本号和最后修改它的 daemon ID，版本号高的胜出，相同时比较 daemon ID。版本号用逻辑计数（每次修改取已见过的最大值加一），不使用系统时间。
- 删除记录时留删除标记，保留 90 天后清理。成员的删除标记永久保留。
- 每台 daemon 上整份数据的上限是 256 KB。

### 协议

新增 RPC 按 `docs/rpc-namespacing.md` 使用 `hosts.sync.*` 等带点命名空间、`.request`/`.response` 成对。能力声明加 `server_info.features.hostSync`。客户端碰到不支持的 daemon 时提示升级那台 host，不做降级兼容（`docs/protocol-compatibility.md` 的功能契约）。daemon 密钥认证是新的认证方式，旧版 daemon 不支持时同样提示升级。

## 必须守住

以下都是用户 2026-11-12 的决定。

- 不做账号系统。
- 任何配置都不能要求打开远端机器自己的 web。把一个能改全部配置的面板暴露到公网不合理，无头服务器也没有 GUI。远端 daemon 的所有配置都从用户手上的客户端下发。
- relay 不存同步数据。
- 没有访客。能连上一台 daemon 就等于拿到它的 shell，产品立场是不要分享。
- 每台 daemon 的远程连接都要有密码，新设备用哪台就输入哪台的密码。
- 同步数据里不含任何密码或 token。
- 端口转发和它的 UI 并入本 epic。

## 不选什么

- 中继服务加账号系统（类似 multica）：违背「代码和数据都在你自己机器上」的产品定位。仓库里以前的 Hub RPC 已经退役，现在所有 `hub.*` 请求都只返回错误（`docs/permissions.md`）。
- relay 保存加密的主机列表（类似 Brave 同步链）：要改 relay 的定位，要处理 Cloudflare 免费计划的限制（整个账号 5 GB 存储，写满后 `RelayMeter` 也会写失败），要清理僵尸链；被移除的设备只要记得链 ID，就能一直拉到密文。
- 只指定一台 daemon 当 home：那台离线时其他设备无法同步。
- 手机、浏览器也作为成员，靠扫码加入：清缓存就会在链上留下僵尸设备，而且没有 daemon 的设备做不了 home。改成客户端不登记、按台输入密码。
- 同步凭据，再用权限收住读取：一台被攻破就全部暴露，移除时还要轮换所有密码。改成同步只放公开信息。
- 隧道权限跟着同步走：被攻破的成员可以往同步数据里写规则，给自己开端口。改成授权只存在目标端本地。
- 整份覆盖的合并方式：两台机器断开期间分别改不同主机，后同步的那份会冲掉另一份。

## 统一语言

实现时最终叫法以 UI 标签为准（`docs/glossary.md`）。

- **同步链**：一个用户全部 daemon 的集合。
- **成员**：链上的一台 daemon。
- **副本**：daemon 上存的那份完整数据。
- **缓存**：客户端在本地存的那份。
- **隧道规则**：「某台 daemon 的某端口，在另一台 daemon 的某端口上可访问」这条配置，存在源端。
- **授权**：目标端本地的一条记录，允许某个 daemon 公钥访问某个端口。

## 推进视图

切片按顺序推进，前一片是后一片的前提。

0. **远程连接必须有密码**。核实 relay 和 SSH 路径的现状，补上「未设密码不能远程使用」的约束。
1. **副本与合并**。daemon 存副本，实现同步 RPC、逐条合并、删除标记、大小上限。验证：单元测试覆盖两份副本断开期间分别修改不同记录、同一条记录、删除记录三种情况，合并结果确定，且与合并顺序无关。
2. **同一台机器上的前端共用一份**。本机前端读写本机副本；第一次运行时把浏览器存储里的旧列表按 `serverId` 导入。验证：桌面客户端和 Chrome 打开的 6777 列表一致，在一边改，另一边能看到。
3. **客户端看到全量列表，按台输入密码**。锁标记、输入和记住密码、主机公钥校验。
4. **daemon 加入和移除**。「设备」页、最后在线时间、`byspace devices` CLI。
5. **隧道**。daemon 密钥认证、目标端本地授权、双向规则、`/tunnels` 规则 UI。

讨论中另外发现一个问题，不属于本 epic：`RelayMeter` 写存储失败时返回 503 并拒绝新连接（`workers/relay/main.go:191`），应改为放行。单独作为一个小修复处理。

## 未确认问题

1. 客户端「记住密码」默认开还是关，记在哪里（浏览器存储、桌面端用系统钥匙串）。
2. 本机回环连接是否继续免密码。现状是免密码。
3. 迁移：浏览器存储里已有的主机条目和 token、`tunnels.json` 里已有的 peer 和密码，怎样迁到新模型，旧数据何时删除。
4. daemon 密钥认证的具体握手方式，复用现有 E2EE 的 daemon 密钥对（配对 offer 里的 `daemonPublicKeyB64`），还是另起一对签名密钥。
5. 一台 daemon 被移除时如果正好离线，它在其他 daemon 上的授权怎么清理（其他 daemon 收到移除记录后自行删除该公钥的授权）。

## 关闭条件

以下几条都要有实测证据：

- 桌面客户端和 Chrome 打开的 6777 看到同一份主机列表，在一边改，另一边能看到。
- 一台从没连过的新设备，用某台 daemon 的密码连上它，看到完整列表；对其他主机分别输入密码后可以使用；清缓存后重新输入密码即可恢复，链上没有新增成员。
- 两台 daemon 在断开期间各改一台不同的主机，恢复连接后两边的修改都保留。
- 篡改同步数据里某台主机的地址后，客户端连接时提示主机公钥不一致并拦下。
- 在一个客户端上新建「笔记本 3425 → VPS 18090」这条规则，全程不打开 VPS 的 web，之后 VPS 上的 `127.0.0.1:18090` 能访问到笔记本的 3425；`tunnels.json` 里不再存对端密码。
- 未设密码的 daemon 不能经 relay 或 SSH 使用。

关闭时把结论合回 `byissue/spec/connection.md`：改写「Daemon 隧道」一节，新增「主机列表同步」一节。同时更新 `docs/architecture.md` 和 `docs/permissions.md`。相关的早期讨论见 [talk 006](../../talks/006-daemon-mesh-tunnel.md)，本 epic 推翻了其中四条：不做反向隧道、入口仅在本机 daemon 在场时显示、隧道要求两端都设密码作为门槛、目标端靠 `allowedPorts` 静态白名单。后两条由目标端按 daemon 公钥的本地授权替代。
