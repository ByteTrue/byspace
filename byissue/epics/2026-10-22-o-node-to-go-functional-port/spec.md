# Node → Go 功能移植

> **读者：** 接手「把 Node 版每一行代码对应的功能都在 Go 里实现出来」的人。
>
> **自检：** 为什么上一个 Epic 失败 · 这一轮的规则 · 怎么判定完成 · 怎么记录。

## 为什么上一个 Epic 没有达成目标

`epics/2026-10-19-x-go-single-binary-full-parity` 的 Issue 009 做的是**只读审计**：
读每个 Node 文件，判断 Go 有没有对应物，给出 `PORTED` / `MISSING` 之类的结论。
512 个文件都拿到了结论，看起来完成了。

但 owner 的要求是「**在 Go 里实现所有 Node 功能**」。审计只是手段。结果：

- 55 个文件被判 `MISSING`（未补的），只有约 4700 行、6 个子系统真的没实现：
  service-proxy 1513、tunnel 777、quota 6 家 ~1500、agent-hooks 3 家 448、
  directory-sync 315、self-update 138。
- 六项里**只有 quota 的阻塞理由成立**（需要真实凭据）。其余五项：
  - tunnel 判 `DROPPED`，理由「需要两台机器」——错，issue 062 早就用 WSL 做过等价验证；
  - directory-sync 判「产品方向未定」——这是我自己猜的，owner 从没说过；
  - service-proxy 判「需要独立设计」——1513 行里大部分是照搬；
  - agent-hooks 判「与只用 pi 的方向一致」——同样是推测。

**根本错误：把「记录为缺失」当成了「已处理」，把「验证条件」当成了「实现前提」。**

## 这一轮的规则

对 `archive/packages/server/src`、`archive/packages/cli/src`、`packages/relay/src`（如果还有）
下的**每一个非测试文件**，按顺序执行：

1. **读这个文件**，理解它做什么。
2. **在 Go 侧找对应实现**（不只是搜函数名，要看行为）。
3. **有 → 记录对应关系**（Go 文件:行 + 一行说明行为如何对上）。
4. **没有 → 实现它**。不是写 Issue，不是写「阻塞条件」，是写代码。
5. **配测试**。测试能反向验证（把实现删掉/改坏，测试要红）。
6. **记录**：文件 → Go 实现 → 测试 → 结论。

### 关于「测不了」

**测不了不等于写不了。** Node 代码摆在那里，逻辑完全可读，所以：

- 能写就写，能测就测——这是默认路径。
- 确实无法端到端验证的（需要第二台物理机、需要真实第三方凭据、需要特定系统），
  **仍然要写实现**，然后：
  - 写它**能测的那部分**测试（单元、in-process、假 CLI）；
  - 在记录里写明「实现的哪一段没有验证过、需要什么条件才能验证」。
- **不允许**因为「无法验证」而跳过实现。这是上一个 Epic 的主要失败模式。

### 关于 DROPPED

`DROPPED` 只用于**已被正式决策移除**的功能，且必须在记录里给出决策出处（issue 编号 +
commit）。已经确认的只有两项：

| 能力     | 决策                                                                  |
| -------- | --------------------------------------------------------------------- |
| Hub      | issue 025，commit `446bc38a3d`，归档 ref `archive/pre-hub-removal`    |
| 插件系统 | issue 025，commit `a5c6bb6588`，归档 ref `archive/pre-plugin-removal` |

「我判断用户不需要」「产品方向未定」「实现风险高」都**不是** DROPPED 的理由。

## 完成标准

**Node 版本每一行代码所对应的功能，都在 Go 侧有对应实现。**

不是「有结论」，不是「有 Issue」，是**有实现**。判定方式：

- 每个非测试文件都有记录，且记录指向具体的 Go 实现（不是「见某处」）。
- 台账里不存在 `MISSING`。允许存在的只有：
  - `PORTED`（有实现，有测试）
  - `PORTED-UNVERIFIED`（有实现，部分路径因外部条件未验证，写明条件）
  - `DROPPED`（有决策出处）
  - `N/A`（类型定义、测试辅助、构建产物，无运行时行为）
- `npm run audit` 全绿，且入站字段缺口为 0（当前 31 条基线来自未实现子系统，实现之后应当归零）。

## 与上一个 Epic 的关系

上一个 Epic 的 `issues/audit-log.md` 有 512 条结论与一张「缺陷总览」表，**仍然有效**，
是本轮的地图：它指出了哪些文件已经对上了、哪些没有。本轮不需要重新发现这些，但需要
**重新判定**——因为上一轮的 `MISSING` 只代表「没实现」，不代表「不能实现」。
