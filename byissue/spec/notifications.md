# 通知送达

> **读者：** 想知道「agent 跑完了」这条消息怎么到达用户，以及为什么不同平台走不同的路。

离开界面之后被叫回来，是 BySpace 的核心旅程之一。daemon 在 agent 需要注意（turn 结束、报错、等权限）和 terminal 需要注意时算出该不该推送，然后按客户端已注册的 token 发出去。**一个 token store，两条传输，按 token 形状分派。**

## 每个平台走哪条

| 客户端             | 通知怎么来                                      | 页面/进程关掉之后    |
| ------------------ | ----------------------------------------------- | -------------------- |
| 浏览器与主屏幕 PWA | Web Push：daemon 直发到浏览器给的 push endpoint | 能收到               |
| Electron 桌面      | 系统通知，由桌面外壳发出                        | 收不到（进程没了）   |
| 原生 App           | Expo 推送                                       | **当前不可用**，见下 |

浏览器在页面开着时也会用 Notification API 本地弹通知；daemon 会按各客户端的在线与聚焦状态决定是走推送还是走应用内提示，不会两条都发。

## Web Push 为什么是这个形状

**VAPID 密钥由每个 daemon 自己生成自己持有。** daemon 是用户自托管的，没有一个中心服务可以替所有人持有推送凭据——塞进公开包等于泄露，让每人自建 Firebase 又和客户端里烧死的 sender ID 对不上。VAPID 把「谁持有凭据」这个问题消掉了：私钥不出 daemon，公钥随 `server_info` 下发。

密钥换掉会让所有已有订阅失效，所以只在密钥文件不存在时生成，不做轮换。

**通知正文对推送网关不可见。** Web Push 强制加密载荷（RFC 8291），密钥来自浏览器。这一点值得单独记住，因为通知正文里带 assistant 消息的开头和权限请求的参数——那些是不该经过第三方明文的东西。

**一个 host 一个 service worker 注册。** 一个注册最多持有一个订阅，而每个 daemon 用自己的密钥签名，推送服务会拒绝公钥与订阅时不符的发送方。所以每个 host 用各自的 scope 注册，互不相干。

**权限必须由用户手势触发**，iOS 尤其严格。所以连接时只在浏览器已经授权的情况下静默订阅，没授权就等用户在设置里点开关，不自动弹窗。

## 约束

- **iOS 只有主屏幕 PWA 有 Web Push**，Safari 标签页里没有。iOS 原生 App 要通知需要 Apple Developer Program 加带 Push 能力的签名，当前发布的 unsigned IPA 走不通。
- **HTTPS 页面与局域网明文直连互斥。** service worker 需要安全上下文，所以要装 PWA、要收推送，页面必须从 HTTPS 源（或 loopback）加载；而 HTTPS 页面不能连非 loopback 的 `ws://`。两者要同时满足，只能走 Relay、`wss://`，或给 daemon 配一张受信证书。细节见 [连接与发布通道](connection.md)。
- **原生推送当前是坏的。** fork 时剥掉了 `extra.eas.projectId`，客户端拿不到 Expo push token。修它需要一个 EAS 项目和 Firebase 凭据；iOS 那一半还额外需要付费开发者账号。Web Push 不依赖这些，所以没有一并修。
- **service worker 不缓存任何东西。** 它只处理推送和通知点击，没有 fetch 处理器。app 与 daemon 本来就会版本漂移，再叠一层缓存会让「用户跑的到底是哪个版本」无法回答。离线外壳缓存要做的话得连同版本化和更新提示一起设计。
- **冷启动点通知不深链。** 已开着窗口时点通知会跳到对应的 agent 或 terminal；没有窗口时只打开应用首页。路由构造在应用内，静态 worker 拿不到。
