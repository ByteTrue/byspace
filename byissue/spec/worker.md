# Worker 与项目组

> **读者：** 想知道「我给人提需求，人自己组队把事办了，回来汇报」这条路径怎么运作，以及哪些约束是刻意为之。

BySpace 原本管的是**会话**：选 workspace、起 agent、读时间线。agent 短暂、无身份、彼此不知情。worker 域长出的是第二种对象：**agent 变成长期实体**，有名字、角色、工作区；多个 worker 组成**项目组**，由一个**协调者**拉人、拆活、派活、汇总、向用户汇报。

入口是独立页 `/workers`（自带侧栏，不套 BySpace 工作壳）。结构化会话与 terminal 两条主线不变。

## 术语

- **Worker** — 长期存在的 agent 实体。一次任务就是它的一个 session。
- **项目组** — 多个 worker 在同一项目上协作的容器，绑 `project_id` 而不是路径，所以 checkout 移动后组仍指向同一项目。
- **协调者** — 组里负责拆解、派活、汇总、汇报的那一个。**一个组恰好一个。**
- **提及即唤醒** — 被点名才会被唤醒；没点名只是可见的上下文。
- **预算** — 一次协作可消耗的公开消息上界。

## 谁说了算由数据库保证

一个组恰好一个协调者，靠**部分唯一索引**而不是应用层检查：

```sql
CREATE UNIQUE INDEX idx_worker_group_one_coordinator
  ON worker_group_members(group_id) WHERE role = 'coordinator';
```

「谁负责」是读的人必须能信的约束，所以让两个协调者在 schema 层**不可表示**。应用层的检查只为给出可读错误 —— SQLite 报的是 `UNIQUE constraint failed: <表>.<列>`，解析那段文本会在改列名的当天失效。

同一原则用在别处：一个组只有一个目标（唯一索引）；一条消息对每个收件人各有一行投递记录（主键是那**一对**）。

## 提及即唤醒，正文不参与路由

发送时 `--mention` 解析成 audience 并让消息成为唤醒消息；非唤醒消息只入流不唤醒任何人。这两者是**两次不同的发送**，不是同一个发送的两个开关。

路由读 audience 表，**从不解析正文**。正文里的 `@名字` 只是呈现 —— 解析正文等于让路由依赖散文。

**可见性与唤醒是两回事。** 收窄谁可读（`privateTo`）不改变是否唤醒。这是照搬上游的区分，不是 BySpace 的发明。

两处实现让这些区分成为**事实而非约定**：

- 只有唤醒消息才写投递行。于是「可见但不唤醒」不是靠代码遵守，而是**没有东西可供收件箱拾取**。
- 给**读不到的人**发消息直接被拒，而不是静默丢掉一半意图。

## 目标与预算

一个组一个目标，带版本、状态和预算。

**写入必须回传读到的版本。** `update/complete/pause/reopen` 都要带 `generation` + `revision`；对不上即被拒。比较与写入是**同一条 UPDATE 语句**，所以不存在两个 run 都以为自己赢了的窗口。`generation` 在 reopen 时递增（新一次尝试），`revision` 在其余变更时递增。

**预算只数公开消息**（未被收窄可见性的），范围 1..96。私密消息不占额度：额度界的是公开说了多少，不是做成这件事花了多少。

**额度触顶停止的是唤醒，不是沟通。** 超限后不能再唤醒任何人，但仍可发非唤醒消息 —— 必须的生命周期更新不该为了省额度而被省掉。触顶后的出路是 reopen 一个新预算，或者让工作停在那里；**为了让额度够用而调高它，正是额度要防的事**。

**reopen 从新的一次尝试计数。** 窗口是**序列边界**（`seq > generation_start_seq`）而不是时间戳：消息序号按组单调分配，时间戳会误判与 reopen 同毫秒发出的消息。

## 任务状态机

九态，一张转换表，**单一写入入口**（`applyTaskTransition`），每次变更都追加历史并记下 actor。越序转换被拒，并返回可达状态；同状态重入不写历史。

```
planned → prepared → assigned → in_progress → submitted → completed | revision | blocked | cancelled
```

后四者为终态：后续工作是**新任务**，就地重开会让「这件事做完了吗」无法只看一行回答。

`blocked` 可从 `assigned` 与 `in_progress` 直接到达，**不必先经过 `submitted`**。一条失败、或被权限挡住的 run 没有产出，要求它先记下一次并未发生的提交，会让审计流水撒谎。

## 权限边界

**skill 里的规则是给模型的对话规则，不改 daemon 的裁决。** worker 技能会要求「建员工前先跟用户确认」，但那条不阻止命令，也不改变 daemon 允许什么 —— 照搬上游自己写明的边界。

真正的边界在权限层：

| 操作                            | 要求               |
| ------------------------------- | ------------------ |
| 读名册、任务、消息流、目标      | `workspace.read`   |
| 建组、改名册、建/改目标、跑任务 | `workspace.write`  |
| **创建 worker**                 | `workspace.manage` |

消息用 `read` 而不是 `write`：发一条、标一条已读都不改工作区状态。按 write 卡的话，worker 得有改项目的权限才能回同事一句话。

## 存储

worker 域有**自己的 SQLite**（`node:sqlite`），与主域的 JSON 文件并存。主域没有迁移框架且每条记录用 Zod 校验；这里需要原子读改写加只追加的历史。分开意味着两边都不用接受对方的持久化规则。

**自带 schema 版本**，当前 v5。加表加索引靠 `CREATE ... IF NOT EXISTS` 自动完成；**改已有的列需要真正的迁移步骤**，版本行是这些步骤判断还差什么用的。v5 是一次真实迁移：把组上的目标文本搬进目标实体，保留数据并按其名册估出预算。
