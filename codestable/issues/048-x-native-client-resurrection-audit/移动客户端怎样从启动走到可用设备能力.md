# 移动客户端怎样从启动走到可用设备能力

## 一句话模型

Paseo `v0.5.1` 的 iOS/Android 客户端已经是完整的 Expo/React Native BySpace UI 宿主，但它仍只是 daemon 的 Controller/Viewer；恢复它可以重新获得系统权限和原生运行时，不能自动得到可被插件寻址的 Device Fabric。

## 当前上游的实际路径

1. `packages/app/app.config.js` 生成 iOS/Android 工程并声明相机、麦克风、推送及原生模块。
2. Expo Router 从 `packages/app/src/app/_layout.tsx` 启动共享 App；Host Profile 决定 Direct WebSocket 或 E2EE Relay 连接。
3. 手机可从 `pair-scan.tsx` 扫描 `#offer=` 配对内容；客户端保存 Host Profile，并以稳定 `clientId` 连接 daemon。
4. AppState、可见性与 15 秒 activity heartbeat 让 daemon 知道客户端前后台状态；恢复前台后重新校验 session/timeline。
5. 平台覆盖文件提供原生文件/图片选择、推送、键盘、Diff/Terminal 渲染、Dictation 与音频能力。
6. daemon 安装的插件仍把客户端 bundle 下发到 App，由 `plugins/evaluate.ts` 在 JS Runtime 中求值并注册 Surface/Panel；没有移动端原生插件包安装机制。

## 上游已经有的能力

- Expo SDK 54 / React Native 0.81 New Architecture 的 iOS/Android 工程配置。
- QR 配对、Direct/Relay 连接、前后台恢复、推送通知路由。
- 本地文件和图片选择、App 沙盒附件、相机扫码。
- 原生与 WebView 两套 Terminal 渲染路径、触摸选区与 iPad 硬件键盘适配。
- `packages/expo-two-way-audio`：Swift/Kotlin 的 PCM 采集与播放，供当前 Voice/音频链路使用。
- Android APK、EAS、TestFlight/Fastlane 相关构建与分发材料。
- 移动端 Maestro/E2E 和若干平台单测。

冻结快照中的相关规模：`packages/expo-two-way-audio` 59 个 tracked files；`packages/app` 有 34 个平台后缀文件、9 个内置模块文件、5 个 Expo Config Plugin 文件，以及约 53 个移动测试/交付文件。

## 上游明确没有的能力

- 手机不是 daemon，也没有 Device Capability Registry。
- daemon/Agent 不能向一个指定手机发起有响应的能力调用。
- 没有 iOS Share Extension 或 Android `ACTION_SEND` 接收链路。
- 没有 ReplayKit Broadcast Upload Extension 或 Android MediaProjection 投屏链路。
- 没有后台剪贴板同步、mDNS/P2P 设备 Mesh、设备级长期密钥和能力授权票据。
- `expo-two-way-audio` 服务于 App 自己的语音体验，不会把手机注册成桌面操作系统可选择的麦克风。

## BySpace 当前缺什么

- `packages/app/src/constants/platform.ts` 把 `isNative` 固定为 `false`；当前共享源码仍有 36 个文件、74 处 `isNative` 引用，但只有 Web 分支实际运行。
- 上游共有 60 个文件、142 处 `isNative` 引用，说明恢复不只是把 `.native.tsx` 文件复制回来；所有共享平台分支都需要重新审计。
- 当前树没有 Expo 原生模块、平台覆盖文件、EAS/Fastlane/Maestro、移动端依赖和发布脚本。
- 当前 Web-only 后形成的新功能和路由必须保留；不能用上游 `packages/app` 整包覆盖。
- 当前 Web 客户端 hello 使用 `clientType: "browser"`，而上游 App 路径使用 `"mobile"`。恢复时应按宿主计算，而不是把 BySpace 当前值或上游值全局硬编码。

## 恢复分类

### 可按当前上游纵向移植

- 原生 Terminal、Diff、文件/图片选择、键盘、push 与音频的当前平台实现。
- 对应 Config Plugin、测试桩和移动自动化用例。
- 前后台 session 恢复与 activity 上报的上游当前行为。

“可移植”不等于无差别复制：必须逐文件套到当前 BySpace 共享组件和当前协议上。

### 机械适配

- npm scope、包名、scheme、路径、环境变量和原生 module namespace 的 Paseo → BySpace 替换。
- App 内目录、通知 category、deep link、资源与文案的品牌替换。
- 当前 protocol/client 的 BySpace API 名称与上游调用点对齐。

### 已确认与必须先决策

- **已确认：** 首轮不制作或发布 iOS 包、不配置 Apple 证书；Android 是首个真实移动宿主。iOS 发布流水线源码仍随客户端迁移保留，但默认休眠且不执行。
- Android 的永久 Application ID、发布主体仍需在实现前确认；iOS Bundle ID、账号和 Secrets 推迟到首次启用发布流水线前确认。
- 是否一开始恢复重型原生 Terminal 渲染，还是先用 WebView renderer 打通构建闭包。
- 推送是否属于首轮闭包；它要求 FCM 等凭证和 daemon 推送基础设施。
- Android 首轮只做内部构建/侧载，不把 Play Store 作为验收门槛。

### 不应恢复

- `v0.2` 删除提交中的旧快照、旧 Chat/Loops、旧协议和已经被当前 BySpace 替代的共享 App 文件。
- 在手机上运行完整 Node daemon。
- 允许插件下载 `.dex`/`.so`/Swift 原生代码；手机原生能力必须由已审核的 App binary 提供。
- 把任何一个插件直接桥接到 React Native `NativeModules`。

## 最小可构建恢复闭包

1. 恢复原生依赖、`app.config.js` 平台段、Expo Config Plugins 和必要 module。
2. 恢复平台覆盖文件，并逐个修复当前共享 App 的平台分支。
3. 先验证 App typecheck 与 Android/iOS `expo prebuild`；Android 进入真实 SDK 编译，iOS 只在具备完整 Xcode 时补 simulator 验证。
4. Android 完成当前 BySpace 的配对、连接、Agent/Workspace、Terminal 和插件 Surface 基本旅程；iOS 保持共享源码与平台编译边界，不作为首轮运行交付物。
5. 在“客户端复活”验收后，才增加 Device Provider 协议；不要把两个未知面一次混进同一提交。

## 冻结基线的验证证据

在 Paseo `v0.5.1` exact commit `f517493591a7b4072aa30ee48db13c1a51495103` 上：

- `npm ci` 成功；
- `npm run build:app-deps` 成功；
- `npm run typecheck --workspace=@getpaseo/app` 成功；
- Android 与 iOS 的 `npx expo prebuild --no-install` 均成功生成工程；上游未配置正式 ID，生成值为 `com.anonymous.paseo`，证明永久标识仍是发布前决策；
- 本机没有 Android SDK、CocoaPods 和可用的完整 Xcode，因此这些结果不是 Android APK 或 iOS archive 的证明。

真实 native build 必须进入后续 Epic 的 CI/EAS 验收，不得把 TypeScript typecheck 当成可发布证明。
