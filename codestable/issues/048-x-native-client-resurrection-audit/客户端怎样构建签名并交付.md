# 客户端怎样构建签名并交付

## 一句话模型

恢复源码和发布客户端是两件事：Android 可先侧载 APK、Electron 可先做 unsigned/internal 包、iOS 可先做 simulator/internal build；永久应用标识、签名、公证、商店政策和 Stable/Beta exact-SHA 发布链必须在对外分发前单独完成。

## 上游已有的交付材料

### Mobile

- `packages/app/eas.json`：development、production、production APK profiles。
- `packages/app/.eas/workflows/`：EAS build 与 iOS beta/release 流程。
- `packages/app/fastlane/`：等待 TestFlight build 并提交审核。
- `.github/workflows/android-apk-release.yml`：Release APK 构建与上传。
- `native-release-version.js`：iOS build number / Android versionCode 派生。

### Desktop

- `packages/desktop/electron-builder.yml`：macOS、Windows、Linux targets。
- macOS after-sign/notarization、GitHub release update metadata。
- Stable/Beta update channel、渐进 rollout 和 packaged smoke/E2E。

这些是移植来源，不是可以原样复制的 BySpace 发布流程。BySpace 已有 exact-SHA CI、不可变 tag、Stable/Beta 隔离和 npm/Cloudflare release 纪律；原生产物必须并入同一 release source of truth。

## 推荐的交付阶段

### Stage A：工程闭包，不公开分发

- Web 继续是正式稳定客户端。
- Electron macOS 先验证 dev 与 unpacked/unsigned package。
- Android 先验证本地 debug/release APK 侧载。
- iOS 只验证共享源码、Expo prebuild，并在具备完整 Xcode 时验证 simulator；不要求签名设备包或 archive。
- iOS/EAS/Fastlane/CI 发布配置随客户端迁移并适配 BySpace，但默认休眠、不配置证书/Secrets、不由 push/tag 自动触发，也不作为首轮门禁。
- 不要求商店 metadata、自动更新或三平台签名阻塞客户端复活。

### Stage B：内部 Beta

- Android GitHub Release APK 或封闭测试。
- macOS Developer ID signed + notarized Beta。
- iOS artifact、证书、TestFlight 和 App Store 全部推迟到用户重新开启 iOS 分发决策后。
- 每个实际产物必须能追溯到同一 BySpace exact SHA 和 channel。

### Stage C：公开分发

- Android Play AAB 与/或官方 APK。
- iOS App Store（只有插件政策和原生能力边界验证后）。
- macOS notarized DMG/zip、Windows signed installer、Linux artifacts。
- Desktop updater 只接受当前 channel 的已签名 metadata 和产物。

## 永久标识与凭据决策

用户已在首轮实施前确认永久标识：

- Android 与未来 iOS：`com.bytetrue.byspace`；
- Android Debug：`com.bytetrue.byspace.debug`；
- Electron：`com.bytetrue.byspace.desktop`；
- 跨平台 deep-link scheme：`byspace`。

这些标识锚定长期发布主体 ByteTrue，不随未来产品域名变化。Google Play package owner、Apple Developer/App Store Connect team、Expo Project ID/EAS account、macOS/Windows signing provider 和全部 Secrets 仍只在对应公开分发阶段确认。iOS 发布流水线源码随 Epic 迁移保留并保持休眠，不因 Bundle ID 已确定就触发发布或要求当前购买证书。

上游 `sh.paseo.*`、`getpaseo` owner、凭据和签名材料仍不得进入 BySpace。

## iOS 动态插件的硬政策门槛

以 2026-08-26 读取的 Apple App Review Guidelines 为准：

- **2.5.2**：App 必须 self-contained，不能下载、安装或执行引入/改变功能的代码。
- **4.7**：Apple 又明确允许未嵌入 binary 的 HTML5/JavaScript mini apps、chatbots 和 plug-ins，但必须满足 4.7.1–4.7.5。
- **4.7.2**：未经 Apple 事先许可，App 不得向这些软件扩展或暴露 native platform APIs/technologies。
- **4.7.3**：向单个插件共享数据或 privacy permission 必须在每次实例中取得明确用户同意。
- **4.7.4**：App 必须提供插件索引和 metadata，并为所有软件提供 universal links。

因此：

1. 上游 `plugins/evaluate.ts` 的动态 JS 本身不是一句“2.5.2 一定禁止”就能定性；4.7 提供了可能路径。
2. 但当前 trusted-local 插件没有 4.7 所要求的索引、universal link、内容/隐私治理证明，App Store 可接受性尚未被证明。
3. 把 microphone/screen/clipboard 等 Native API 直接暴露给下载的插件，会正面撞上 4.7.2；首轮不能这样设计。
4. iOS 应让固定 BySpace native UI 明确启动能力，并按次同意；插件通过 daemon 取得结果。即使这样仍属于需要真实 App Review 验证的灰区，不能承诺上架。
5. 在政策验证完成前，iOS 内部 build 可以关闭动态插件客户端 bundle，或只允许随 App 审核的 first-party surfaces；Web/Electron/Android 不必被迫采用同一限制。

官方来源：<https://developer.apple.com/app-store/review/guidelines/>。

## Android 动态代码与前台能力

Google Play Device and Network Abuse Policy 明确：

- Play App 不得从 Play 之外下载 dex、JAR、`.so` 等 executable code；
- VM/interpreter 中、只间接访问 Android API 的代码（例如 WebView/browser JavaScript）有例外；
- runtime-loaded interpreted code 仍不得允许违反 Play 政策；
- Android 14+ 的 Foreground Service type 必须声明，且能力要与核心功能相关、用户发起或可感知、可停止、只运行必要时长。

所以 Android 可以优先验证纯 JS 插件 UI，但 native bridge 必须是固定 allowlist；麦克风和 MediaProjection 必须使用显式前台服务、持续通知和用户可停止状态。

官方来源：<https://support.google.com/googleplay/android-developer/answer/9888379>。

## 移动 OS 能力的产品约束

- 麦克风/屏幕必须有系统权限和明显活动指示，不能做“静默监听”。
- iOS 全局投屏需要 ReplayKit Broadcast Upload Extension；Android 需要 MediaProjection 与 foreground service。
- iOS/Android 都不适合承诺后台无感剪贴板同步；应改为前台按钮、PasteControl、Share Extension/Send Intent 等用户动作。
- iOS Share Extension 应保持轻量，只把内容写入 App Group queue；不要在 extension 进程启动完整 React Native/插件 runtime。
- EAS Update 只能更新 JS/assets；新增 native module、权限或 extension 必须发布新 binary。

这些是能力设计输入，不是恢复上游 App 后自动解决的事项。

## Desktop 分发边界

- macOS 站外正式分发需要 Developer ID 签名和 notarization；Electron/Node 的 Hardened Runtime entitlements 必须由真实 package 验证。
- Windows 正式分发若不签名会受到 SmartScreen 信任警告；代码签名应由 CI 中受控凭据/HSM 服务完成。
- Linux 可以较早提供 artifact，但 AppImage/deb/rpm 的 daemon、数据目录和 updater 行为仍要做真实 smoke。
- Mac App Store 对 sandbox、自更新、后台进程和安装额外组件限制更强；BySpace 的托管 daemon、插件与未来 helper/driver 更适合 Developer ID 站外分发。

## 当前验证状态

冻结 Paseo `v0.5.1` 基线已经证明：

- App dependencies build 与 App typecheck 通过；
- Android/iOS `expo prebuild --no-install` 均成功，但因上游没有正式 identifier，生成的是 `com.anonymous.paseo`；
- 生成 server declarations 后，Electron main TypeScript build 通过；
- `npm run build:desktop -- --dir` 成功导出 renderer 并打出 macOS arm64 App，但只做 ad-hoc signature，未 notarize；
- 本机缺 Android SDK、CocoaPods 和可用完整 Xcode，不能声称 Android/iOS native build 已通过；
- 真实安装 smoke、正式签名、公证、TestFlight/Play 和设备权限均未验证。

后续 Epic 的“完成”必须区分 Source Closure、Unsigned Artifact、Signed Beta、Public Distribution 四个门槛，不得用一个绿色 typecheck 覆盖全部。
