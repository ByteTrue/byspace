# 插件怎样调用跨设备能力

## 一句话模型

恢复客户端只会产生多个 BySpace UI 入口；Device Fabric 还需要把每个原生客户端注册成有独立身份、在线状态、能力清单和端侧授权的 Capability Provider，再由 daemon 安全地代表插件或用户调用它。

## 现有原语可以复用什么

### 控制连接与客户端状态

- 客户端已经有稳定 `clientId`、`clientType`、Host Profile、activity heartbeat 和 server → client 事件。
- 这些足以做在线状态与 UX 关联，但 `clientId` 不是设备安全身份：共享 daemon 凭据的客户端可以声称相同 ID。
- Device Provider 需要独立生成并保存设备密钥，经 daemon enrollment 后用 challenge proof 绑定当前 connection 与已批准设备。

### Blob / 文件传输

- `packages/protocol/src/file-transfer.ts` 已定义二进制 file frame：magic、version、transferId、offset、totalSize 与 payload。
- `DaemonClient.uploadFile()` 已使用 64 KiB chunk、SHA-256 和 upload request/response。
- 这可作为首个 File Handoff 的基础，但当前调用先持有完整 `Uint8Array`，没有面向跨设备投递的收件人、持久化队列、断点续传或显式 credit window。

### 持续 Stream

- Remote Web Services 的 `RemoteByteStream` 已有 session binding、严格 sequence 和 credit-based backpressure。
- Standalone Data Relay 已有盲配对转发与独立 WSS data plane。
- 这些适合复用协议思想和底层状态机，但现有业务语义绑定 daemon ↔ daemon、mapping ↔ loopback port；不能把手机能力伪装成 RWS 端口。

### 插件层

- Plugin server process 与 browser client bundle 已有 typed request/response RPC、Surface/Panel/Command Center。
- 现有 Plugin RPC 是 JSON request/response，没有 subscription、binary stream 和设备权限模型；不应传麦克风、视频或大文件。
- 插件 server 当前是 trusted-local、无沙箱 Node。即使首期只支持可信插件，device key、Relay credential 和 OS handle 也必须由核心持有。

## 最小核心对象

### Device

建议由 daemon 持久化：

- `deviceId`：daemon 分配的稳定 ID；
- `publicKey`：端侧长期设备公钥；
- `displayName`、`platform`、`appVersion`；
- enrollment/revocation 状态；
- 最近在线时间与当前 connection binding。

设备 display name 和现有 `clientId` 可用于迁移/UX，但不能替代 key proof。

### Capability Descriptor

固定、版本化、由客户端 binary 声明，例如：

- `device.files.pick@1`
- `device.audio.input@1`
- `device.screen.broadcast@1`
- `device.clipboard.readOnce@1`
- `desktop.audio.virtualInput@1`
- `desktop.editor.openTarget@1`

首期不要允许插件注册任意 Native Capability。新增能力意味着升级受信任客户端 binary、声明平台权限并补测试。

### Grant 与 Consent

两层都要存在：

1. **Daemon grant**：用户允许某插件/系统调用某设备上的某项能力，可撤销、可审计。
2. **Device consent**：设备端在调用当下根据风险、前台状态和平台政策决定允许、拒绝或要求交互。

持久 grant 不能覆盖系统权限，也不能让高风险能力静默启动。iOS 动态插件场景还可能要求每次显式同意，不能只依赖“一次永久允许”。

### Invocation

需要 daemon → 指定 connection 的有响应请求，而不是普通广播事件：

- request 有 `invocationId`、`deviceId`、capability/version、validated input、deadline；
- device 返回 accepted/denied/unavailable/suspended/expired 或 result/stream ticket；
- 断线、App background/suspended、调用方取消和 daemon restart 都有确定结果；
- deadline 后的迟到响应必须丢弃，不能命中后续 invocation。

新 wire message 必须使用 dotted namespace 和 `.request/.response`，字段保持向后兼容，并通过 `server_info.features.*` 单点 gate 新功能。

## Event / Blob / Stream 的边界

- **Event**：设备上线、授权结果、剪贴板“有可发送内容”、文件到达等小型结构化通知，走主控制连接。
- **Blob**：有限大小文件/图片，首期可扩展现有 file transfer；加入 source/target、流式读取、credit、校验、取消和清理。
- **Stream**：麦克风、屏幕和摄像头，使用独立 data connection；控制连接只交换 offer/ticket/state。

不要把持续二进制塞进 Plugin JSON RPC，也不要让音视频与 timeline/control heartbeat 在同一条拥塞队列中竞争。

## 插件调用路径

推荐路径：

```text
Plugin Surface
  -> plugin server typed RPC
  -> daemon Device Capability Service
  -> grant + target-online + policy check
  -> addressed device invocation
  -> device-side native consent
  -> Event / Blob / Stream data plane
  -> plugin server receives typed result or opaque stream handle
```

插件永远不直接拿设备私钥、Relay token、preload IPC 或 native module。对于 iOS，首轮更安全的产品形态是“插件发出请求，BySpace 固定原生界面由用户明确启动能力”，而不是让下载的插件 JS 直接调用 Native API。

## 建议的首轮范围

### Scope 0：只恢复客户端

- Electron 与 Android/iOS 能构建、配对并使用当前 BySpace 主旅程。
- 不新增 Device 协议，避免把“客户端复活”和“新分布式协议”同时调试。

### Scope 1：前台 File Handoff

先做 Android + Electron，同一 daemon 内：

1. 设备 enrollment 和在线 registry；
2. Electron/插件请求 `device.files.pick@1`；
3. Android 固定原生 UI 展示来源、目标和用户确认，调用系统 picker；
4. 文件通过扩展后的 Blob transfer 送到 daemon，再由 Electron 选择落盘位置；
5. 拒绝、离线、取消、校验失败和断线都有确定结果。

这个切片验证反向寻址、端侧 consent、Blob、插件边界和客户端生命周期，且不先引入音视频抖动问题。

### Scope 2：Phone Mic Monitor

- 手机前台明确开始麦克风采集；
- 独立 E2EE stream 与 credit backpressure；
- Electron 先只播放/监控收到的音频；
- 验证慢网、锁屏、权限拒绝、来电中断、断线和停止。

### Scope 3：OS-wide Virtual Microphone

- 在 Stream 稳定后再接 macOS/Windows/Linux adapter；
- driver/helper 单独安装、签名、升级和卸载；
- 这是“让所有桌面应用可选择手机麦克风”的真正完成条件。

## 首期明确不做

- 跨多个 daemon 的 Device Mesh、P2P/ICE/TURN、任意 TCP tunnel。
- 后台无感剪贴板同步；移动 OS 本身不允许通用 App 在后台持续读取剪贴板。
- 让第三方插件下载和运行 native code。
- 以 Remote Web Service 的 loopback port grant 代替方法级设备授权。
- 在公共插件市场、安全隔离与签名尚未设计前宣称支持任意第三方插件。
