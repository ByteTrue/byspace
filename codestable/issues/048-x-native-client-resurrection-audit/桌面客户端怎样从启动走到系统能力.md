# 桌面客户端怎样从启动走到系统能力

> **关闭后追加决策（2026-08-26）：** 本文原先把 Browser Automation 建议为首轮后置项。用户随后明确要求恢复旧裁剪一起移除的大部分受维护原生/桌面内容；因此 Browser workbench/CDP、Browser tools/protocol、auto-updater/rollout、平台测试与打包发布源码现已纳入 Epic 005。真实签名发布仍单独开闸。

## 一句话模型

Paseo `v0.5.1` 的 Electron 客户端不是第二套 UI，而是共享 Expo Web App 的本地宿主：它管理窗口、preload 权限桥、daemon、local socket、文件和系统集成；因此它是 BySpace Desktop Capability Host 最合适的起点，但现有代码还没有虚拟麦克风等系统级适配器。

## 当前上游的实际路径

1. `packages/desktop/src/main.ts` 启动 Electron 主进程，取得单实例锁、注册私有 scheme，并创建 BrowserWindow。
2. 开发时 Renderer 加载 Expo dev server；生产时通过私有 protocol 加载 `packages/app/dist` 的共享 Web SPA。
3. BrowserWindow 保持 `nodeIntegration: false` 与 `contextIsolation: true`，`preload.ts` 只暴露有界的 `window.paseoDesktop` 命令和事件。
4. Desktop 可用 Electron/Helper 作为 Node runtime 拉起脱钩 daemon，并处理版本匹配、PID、退出和本地状态。
5. Renderer 不能直接访问 Unix domain socket / Windows named pipe，因此 main 进程的 local transport 经 Electron IPC 转发文本和二进制帧。
6. 对话框、通知、编辑器跳转、文件拖放路径、窗口状态、菜单、更新和内嵌 webview/CDP 等系统能力由 main/preload 提供。

## 上游已经有的能力

- Electron 主进程、隔离 preload、窗口与多屏状态、菜单、deep link、原生通知。
- 托管 daemon、捆绑 CLI、登录 shell 环境继承与 local IPC transport。
- 文件/目录选择、拖放真实路径、managed attachment、外部编辑器探测与定位跳转。
- GitHub Release 自动更新、Stable/Beta channel 和渐进放量机制。
- 内嵌 webview 与 CDP browser automation，包括可信输入、快照、截图和日志。
- Electron Builder 的 macOS、Windows、Linux 产物配置和相关 smoke/E2E。

冻结快照的 `packages/desktop` 有 183 个 tracked files，其中 126 个位于 `src/`。当前 BySpace 整包缺失。

## Electron 能做什么，什么仍需 OS 组件

### Electron/Node 直接可提供

- 剪贴板读写和变化轮询、系统通知、菜单、托盘/Dock、全局快捷键。
- 文件选择、拖放、目录监听、子进程和登录会话中的本地 IPC。
- 屏幕/窗口枚举与捕获入口；具体系统音频能力仍要分别接 macOS/Windows 公共 API。
- Capability Host 的常驻用户会话进程、可见授权 UI 和停止入口。

### 需要独立 helper、插件或驱动

- 让 Zoom、会议软件等第三方应用把“手机麦克风”看成系统输入设备：
  - macOS 需要 CoreAudio Audio Server Plugin / AudioDriverKit 路径；
  - Windows 需要虚拟音频设备驱动；
  - Linux 可优先使用 PipeWire/PulseAudio 虚拟 source，通常不需要自定义内核驱动。
- 某些 macOS TCC 能力、Windows 安装器提权、开机启动和驱动安装需要签名 helper/installer。
- Electron 可以捕获/播放音频，不等于可以向操作系统注册虚拟麦克风。

虚拟麦克风应作为独立的 platform adapter 切片，有单独安装、签名、卸载和故障恢复，不应塞进普通插件 JS。

## BySpace 当前缺什么

- 没有 `packages/desktop`、`packages/app/src/desktop`、`.electron.*` 覆盖层和 Electron 依赖。
- 没有 local socket bridge、托管 daemon、desktop deep link、更新和打包发布链。
- 当前 `AGENTS.md` 与 Project Spec 明确禁止 Electron；开始实现前必须先由批准的新 Vision/Epic 改变这条产品边界。
- 当前 daemon 的版本、目录、CLI token、配置与上游已经存在 BySpace 差异，不能直接照搬 Paseo daemon manager。
- 当前 BySpace 已有新的 release exact-SHA、Stable/Beta、Cloudflare 与 npm 纪律；Electron release 必须接入这套规则，不能复制上游 workflow 后形成第二套真相。

## 恢复分类

### 可按当前上游纵向移植

- Window/preload/local transport/daemon manager 的结构和测试。
- Dialog、notification、file path、editor target、login shell env 等宿主能力。
- Electron Builder 的平台矩阵作为起点。

### 机械适配

- npm scope、env prefix、scheme、IPC channel、global preload 名称、app data 路径与资源的 BySpace 化。
- 使用当前 `@bytetrue/byspace-server`、CLI 和当前 daemon config/lifecycle。
- 更新产物名称、GitHub repo、Stable/Beta channel 与 release metadata。

### 已决策与仍需发行开闸的边界

- Desktop 保留上游 managed daemon 模式，同时允许连接其他 Host；否则会失去完整桌面入口的主要价值。
- Browser Automation 已确认属于本次完整恢复，按独立可验证 checkpoint 移植完整 UI/preload/broker/protocol/server/tool/test 纵向切片。
- 源码从第一天保持 macOS/Windows/Linux 边界；首轮产物可先在 macOS 验证，但不能删掉其他平台实现、测试或打包配置。
- 永久 Desktop `appId` 为 `com.bytetrue.byspace.desktop`，自定义 scheme 为 `byspace`；更新 repo、签名主体与公开 channel 仍在真实发布前确认。
- Mac App Store 还是 Developer ID 站外分发仍属于后续发行决策。托管 daemon、自更新和插件模型更适合 Developer ID/notarized 分发，不建议把 Mac App Store 作为首轮目标。

### 不应恢复

- 旧 `v0.2` Desktop 快照和已经被当前产品替代的 renderer UI。
- 旧迁移 shim、旧 Chat/Loops、用 Paseo marketing-site 替换现有 BySpace website，或未经批准的真实签名/商店发布执行。
- 在 Renderer 或插件 bundle 中开放任意 Electron IPC/CDP；所有系统能力必须经过 typed preload/broker。

## 作为 Capability Host 的目标边界

Electron main process 应成为桌面设备能力的可信宿主：

- 它向 daemon 注册固定、版本化的 capability；
- 它在本地展示授权、活动指示和停止入口；
- 它持有 OS 权限和 helper 连接；
- Renderer/插件只通过 daemon 的受控能力 API 发起请求；
- 插件拿不到 long-term device key、Relay token、任意 IPC channel 或 driver handle。

这比让 daemon 直接读取桌面 session 更稳：Windows service 的 Session 0、macOS GUI/TCC 和 Linux display session 都说明“后台 daemon”与“登录用户的系统能力宿主”不是同一责任。

## 冻结基线的验证证据

在 Paseo `v0.5.1` exact commit 上：

- 先运行 `npm run build:server` 生成当前 workspace declarations；
- 再运行 `npm run build:main --workspace=@getpaseo/desktop`，Desktop TypeScript main build 成功；
- `npm run build:desktop -- --dir` 成功导出 Electron renderer 并生成 `release/mac-arm64/Paseo.app`；
- 该本地包只使用 ad-hoc signature，electron-builder 明确跳过 notarization，不是可公开分发的签名产物。

若跳过 server build，Desktop 会因找不到 `@getpaseo/server` declarations 失败；这是 workspace build 顺序，不是应通过本地重复类型修补的源码缺陷。真实安装、运行 smoke、Developer ID/Windows 签名和 notarization 仍需后续验证。
