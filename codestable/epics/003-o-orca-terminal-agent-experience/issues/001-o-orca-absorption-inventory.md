# 产出 orca terminal agent 体验吸收清单

> **读者：** 做这份对照的人。要产出什么、按什么维度判断、哪些不用查、结论交给谁排序。

---

## 做成以后是什么样

一份可排序的清单，Owner 看完能直接圈出「做这几项」。每一项回答五件事：

1. **本仓库现状** —— 现在是怎样的，缺什么，有没有相关已关闭 Issue。
2. **orca 的做法** —— 具体行为，加源码落点。
3. **对用户的差别** —— 采纳后用户能多做什么或少忍受什么。不能用一句话说清差别的项直接判为不值得。
4. **代价** —— 要改哪些包、是否触及协议、是否需要真机验证、是否影响结构化会话。
5. **建议** —— 采纳 / 不采纳 / 需要先验证可行性，附理由。

**范围：** Epic spec 候选表里的六项，加对照过程中发现的新项。只做判断与排序，不写实现代码。

**不包含：** 任何吸收项的实现；orca 的架构、Kanban、Design Mode、SSH worktree、browser 等未点名区域；对结构化会话的改动。

**顺序建议：** `codestable/issues/019-o-sync-upstream-to-0-8-0-beta.md` 的全量同步先完成，本 Issue 的结论才建立在同步后的现状上。判断工作本身不阻塞，但结论要在同步后复核一次。

## 为什么现在做

Epic 已确认「只做吸收」，但吸收什么、按什么顺序还没定。先出清单再动手，避免按印象挑活。Owner 的手机端体验是直接触发：全屏 TUI 在手机上基本不可用，说明手机端可用性那几项优先级可能高于生命周期档位。

## 现状怎么工作

terminal 会话的活动链路：daemon 创建 shell 时注入 `BYSPACE_TERMINAL_ID` 等环境变量；各 agent 的 hook 装进自己的配置目录，把事件 POST 给 daemon 的活动端点；`TerminalActivityTracker` 在状态转换时驱动圆点、workspace 汇总与通知。现有 hook provider 有 claude、codex、opencode、pi 四个。完整说明见 `docs/terminal-activity.md`，落点 `packages/server/src/terminal/agent-hooks/`。

启动方式目前没有命令表：terminal 就是 shell，用户自己敲命令起 agent。

## 判断维度

对每一项按同一套问题走，避免有的项写成长文、有的只写一句：

- 这一项服务哪个用户场景，在哪个设备上。
- 本仓库缺的是能力还是打磨。缺能力优先。
- 是否触及协议。触及则要按 `docs/protocol-compatibility.md` 处理，代价上调。
- 是否需要真机验证。需要则代价上调。
- 是否可能影响结构化会话。可能则默认不采纳，除非能证明隔离。

## 需要额外查证的两项

其余四项照上表对照即可，这两项判断依赖事实而非偏好：

- **转录投影视图对 Pi 是否可行。** orca 的支持列表不含 Pi。本仓库 Pi provider 已把 Pi 的会话文件作为原生句柄跟踪，需要确认：文件格式是否稳定可解析、是否随 turn 增量追加、能否只读跟随而不干扰 Pi 自身写入。不通则该项只能覆盖部分 agent，价值大幅下降。
- **四档状态的 hook 事件映射。** 现有四个 hook provider 各自能否区分「等权限」与「等输入」。若某个 agent 的 hook 事件本身不区分，这一档对它就是做不到的，不能只在 UI 上加个状态。

## 验证

- 清单的每一项都有源码落点或命令输出作为证据，不写「据说」。
- 上述两项查证给出明确的通或不通，不通则写清卡在哪。
- 交付形式：写回本 Issue，Owner 排序后再由 Epic spec 登记采纳项。
